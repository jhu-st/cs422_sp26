Simplifying before debugging

Sometimes the program state or program output is too huge to tackle at once or even to attempt to develop meaningful debugging hypotheses. Remember that we oftentimes deal with thousands of lines of code, millions of execution states, and hundreds of variables. Without simplification, we would be trying to explain a failure in a massive, high-dimensional space. Thus, it may indeed make sense to first find and rule out irrelevant parts to the failure at hand; in other words, simplify to only relevant parts.

An an extreme example, imagine a plane crashes (i.e., failure) and we have no idea what could have caused it. Before you attempt to even debug the failure, it makes sense to exclude the components that did NOT cause the failure. This will help up us to only keep and focus on the relevant parts that could have in fact caused the failure. So we try the followings:

  • remove passenger seats, does it still crash? Yes → seats are NOT relevant
  • remove coffee machine, does it still crash? Yes → coffee machines are NOT relevant
  • Remove the engines, it does not move and does not crash → engines are relevant!
core idea

You cannot understand everything → remove everything, one by one, that doesn't matter.

A real example:#

Back in the 90s, The Gecko rendering engine used by Mozilla browser experienced a crash when loading a large HTML file of approximately 896 lines. At the time, developers were overwhelmed with hundreds of bug reports, making it difficult to analyze each issue in detail.

Rather than attempting to debug the full, complex input, developers adopted a systematic simplification strategy:

  • They repeatedly removed portions of the HTML input
  • After each removal, they checked whether the failure still occurred
  • Any part of the input that was not necessary to reproduce the crash was discarded

This process was often carried out using a binary search–like approach, progressively reducing the input size (e.g., 896 → 448 → 224 → …).

Eventually, the failure was reduced to a single line of HTML:

<SELECT NAME="priority" MULTIPLE SIZE=7>

This dramatically simplified the test case.

Benefits of simplification:#

  • Make it easier to understand and reproduce the bug
  • Enable developers to quickly identify the root cause
  • Allow clear communication of the issue to others and inside development teams
