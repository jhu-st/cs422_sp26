Debugging as Search in Time and Space

When you run a faulty program, an error occurs somewhere in the program which may results in an observable failure. Take a look the pictures below:

  • Horizontal dimension → program variables (state space)
  • Vertical dimension → time (execution steps)
  • Most states are marked ✔ (correct)
  • Failures/errors appears as ❌ at some point


You observe a failure in the output. The question is what caused it:

The reason is a fault was excuted resulting in an error which then in return was propagated into a failure:

Key Insights

Debugging involves answering:

  • “Where did things first go wrong?”

Not:

  • “Where did the failure appear?”

Key Insight:
The failure is just the symptom
The fault is somewhere earlier in time

Debuggin#

As a debugger, when facing a failure, you would need to find the potential "origins":

The origins are the possible root causes of a failure. There is a point in the program up to which execution proceeds as expected, with no errors. However, because a fault exists and is executed beyond that point, it introduces an error into the program state, which eventually manifests as a failure in the output:

Once you find the right origin(s) and fix them, the erros and failure go away. This is called debugging!

Debugging is Hard

Debugging is hard becuase:

  • A single program state can include many variables
  • A program may go through millions of states

How failure comes to be in three stages:#

A failure comes to be in three stages:

  • The programmer makes a fault by creating a defect in the code
  • The defect causes an infection (i.e., incorrect state or error)
  • The infection causes a failure -- an externally visible error :::
caution

Not every defect results in an infection, and not every infection/error results in a failure.
